# Albiex Synth City rename: compatibility design for runtime identifiers

**Issue:** #789. **Source pin:** `585af8b7c0339e9e87c41d802127da2d5176b697` (master as merged through PR #796). **Scope:** this file only; it designs behaviour for a later implementation team and changes no code. **Parent:** #787. **Input:** the merged inventory in this folder (`inventory.md`, measured at its own earlier pin `94cb599a98d6`); every code line cited below was re-verified at the pin above, and line numbers refer to that pin.

## Summary for the reader

This document designs how every runtime identifier that carries the old product name is replaced when **Albiex Synth City** v4.0.0 replaces Claude Deck v3.1. Later mentions shorten the product name to Synth City; that shortening is presentation only and does not decide any identifier.

The Director's current rules, recorded in `inventory.md` section 7, shape the whole design:

- the rename release is **v4.0.0**, with no version reset;
- there is **no deprecation window and no parallel old-name support**: after the upgrade the product does not read, accept or answer to the old names alongside the new ones;
- the one exception in kind is a **one-time automatic move**: on its first start, v4.0.0 moves the existing database file and the existing backups folder to their new names, retaining every team, setting and history with no manual step by the operator.

"No parallel support" and "one-time move" are different things, and this design keeps them apart throughout. A move happens once, during the first start of the new version, and afterwards only the new name exists. Nothing in this design reads both an old and a new name as an ongoing input, aliases an old tool name to a new one, or keeps an old header working. Where data created under an old name must survive — the database, backups, installer-written agent configuration, browser storage — the design moves or rewrites that data once, as part of the standard upgrade, never by asking the operator to run a separate repair command.

Exact new spellings are **proposals for the Director**, collected in section 3. The behaviour design (ordering, conflicts, crash safety, tests) does not depend on which spelling is chosen; if the Director picks a different scheme, the names substitute mechanically. Nothing here implements, transfers or deploys anything; #791 turns the user-visible parts of this design into the migration guide and release notes.

### 1.2 Terms used in the tables

- **Replacement name** — the proposed new identifier. Every replacement name in this document is a proposal (section 3), not a decided fact.
- **Old-name duration** — how long the old identifier keeps working after v4.0.0 starts. Under the decided rules this is **none** for every family; each family section states it explicitly rather than leaving it implied.
- **First-start behaviour** — what the standard upgrade does automatically the first time v4.0.0 runs: nothing (paired components simply ship together), a one-time data move, or a one-time rewrite of configuration the product itself installed.
- **Deck-owned configuration** — entries in a user's agent configuration files that meet the provider-specific *evidence standard* in section 4.2 (a bare name match is never enough). Only evidence-qualified configuration is rewritten automatically. Everything else the operator wrote or changed by hand (shell exports, custom service files, hand-edited or ambiguous entries) is never rewritten; section 4 states per family what breaks and what the operator must rename, which #791 must document.
- **Manual step** — any operator action beyond performing the standard upgrade (stopping the old version and starting the new one by whatever method the operator already uses). The normal upgrade path designed here needs none. Deliberately ambiguous states (both old and new database present with data) stop safely and ask for a human; that is a conflict outcome, not the normal path.

### 1.3 The compatibility surface

The surface is the inventory's runtime-identifier class (377 lines, `inventory.md` section 4.1) plus the supplemental families indexed in its section 3.4: bare-`Deck` headers and commit trailers, the joined OpenCode export and old domain, the 36 `deck_` Agent Mail tools and 46 other `deck_` tokens, systemd unit filenames, and the backend package name. Section 4 covers each family once. Pure copy (the inventory's user-facing and docs classes) and history are out of scope except where a string is both copy and a recognised marker.

## 3. Proposed new names (Director choices)

Two coherent spelling schemes cover almost every family. The design tables use the **recommended** spelling, but neither scheme is approved by being written here; the examples carried over from earlier issues (`synth-city`, `SYNTH_CITY`) were illustrations, not decisions.

| Scheme | Shape | Strengths | Costs |
|---|---|---|---|
| **S — short product name** | `SYNTH_CITY_*`, `synth_city_*`, `X-Synth-City-*`, `synth_city.db`, `~/.synth-city` | Readable; tool and prompt text stays short; mirrors the decided repository name `albiexai/synth-city` | The Albiex qualifier is absent from the identifier itself; "Synth City" alone carries the moderate naming risk noted in `website-and-docs.md` section 4.7 |
| **Q — fully qualified** | `ALBIEX_SYNTH_CITY_*`, `albiex_synth_city_*`, `X-Albiex-Synth-City-*`, `albiex_synth_city.db`, `~/.albiex-synth-city` | Unambiguously Albiex's in every shared namespace | Every tool name, environment line and generated prompt grows by the qualifier on every use |

**Recommendation.** Use scheme S for identifiers that only ever pass between this product's own paired components (launcher-to-child environment variables, MCP tool names served by this product's own shim, headers between its own frontend, shim and backend), because those components are always installed and presented as Albiex Synth City together. Use scheme Q for names registered in namespaces shared with other software, where an unqualified name could collide or imply the wrong owner: package names, release artifacts, systemd units and install paths, the MCP server name written into third-party agent configuration, and the home data folder. This follows the existing rule that packages and commands must not be bare `synthcity` and should use `albiex` or `albiex-synth-city` (`website-and-docs.md` section 4.7). If the Director prefers one scheme everywhere, the substitution is mechanical and no behaviour in section 4 changes — with one binding exception: “S everywhere” never applies to packages, commands, release artifacts, units or the MCP server name, which keep the qualified `albiex…` spellings the existing rule requires (`website-and-docs.md` section 4.7). Scheme choice is free only where this document marks it as a choice.

### 4.2 MCP server name and the installer

**Old-name duration: none.** v4.0.0 serves and registers only the new MCP server name. The old registration in a user's agent configuration is removed once, automatically, and replaced — it is never left working in parallel.

Current state at the pin: one constant names the server everywhere (`MCP_SERVER_NAME = "claude-deck-mail"`, `backend/app/services/agent_mail_install_service.py:34`), the shim serves under the same literal (`FastMCP("claude-deck-mail")`, `backend/mcp_shim/agent_mail_server.py:22`), and per-provider apply/uninstall functions register or remove that name plus the product's hooks:

|---|---|---|
| Claude Code | `apply_claude_code_install` / `uninstall_claude_code` (`:897`, `:932`; server lookup `:858`, `:915–918`, `:936–937`) | MCP server entry + hooks in user settings, with group-B environment values |

| OpenCode | `apply_opencode_install` / `uninstall_opencode` (`:1033`, `:1050`; detection `:568–577`) | MCP entry in `opencode.json(c)` (`:100–107`) + a generated plugin **file** at `…/plugins/claude-deck-agent-mail.js` (`:110–111`; provider descriptor `backend/app/services/providers/opencode_cli.py:39`) recognised by its marker text (`_OPENCODE_PLUGIN_MARKER`, `:65`, written via the template at `:582` onward, tested at `:684`, `:1068`) and exporting `ClaudeDeckAgentMailPlugin` (`:599`) |
| Muse | `apply_muse_install` / `uninstall_muse` (`:1134`, `:1152`; detection `:803–805`) | MCP server entry in Muse settings with group-B environment values (`:776`) |
Pi is deliberately **not** in this table as an installed MCP registration: nothing registers an MCP server for Pi. The bridge injects group-B′ environment and the extension at launch (`backend/app/services/agent_bridge/spawn.py:85–92`; `backend/app/services/pi_mail_readiness.py:40–50`), and the shipped extension registers the generated manifest's tools (`integrations/pi-agent-mail/extension.ts:35–36`). The Pi client also hard-codes old-name runtime artefacts (`claude-deck-pi` client name and per-run `/tmp/claude-deck-pi-…` directory, `integrations/pi-agent-mail/client.ts:88–91`, `:139`) which rename with the code and need no data move. Pi therefore gets its own first-launch behaviour in section 4.3 and its own test (T-P1), not the rewrite below.

**Design — one-time, evidence-gated rewrite during the standard upgrade.** The upgrade adds a persisted, staged rewrite that runs automatically on the first start of v4.0.0 (sequencing in section 5). It may reuse apply/uninstall *mechanics*, but it must not reuse their detection as proof of ownership, and it must not reuse `_backup_before_mutation` as its transaction barrier.

*Ownership evidence, per provider.* A matching server name alone proves nothing: the current checks are a name-presence lookup for Claude Code (`:858`, `:915–918`), a substring test on CLI output for Codex (`:512–518`), a key-presence test for Copilot (`:524–534`), and a Muse settings lookup (`:803–805`). A hand-written entry can satisfy every one of them, and OpenCode's “current entry” test is stricter in the wrong way — it requires the generated URL, so a legitimate operator-customised URL fails it (`:540–564`). The rewrite therefore classifies each discovered old-name entry before touching it, capturing its full value set first:

| Provider | Minimum evidence to treat an entry as product-installed | Ambiguous when |
|---|---|---|
| Claude Code, Muse | Old server name **and** command/args resolving to this installation's shim path (`shim_path()` shape, `:73–74`) **and** the generated hook entries the installer writes are present or were recorded | Name matches but command/transport points elsewhere, or hooks shape is unrecognised → leave untouched, report needs-attention |
| Codex, Copilot | Old server name in parsed `mcp list` output **and** the entry's command resolves to this shim **and** the product's hooks file/entries are present (Codex `:92`; Copilot filename `:96–97`) | Name present but any corroborating item is missing or contradictory → untouched, needs-attention |
| OpenCode — **per artifact, independently** | *MCP entry:* command resolves to this shim (the URL value is *captured as a customised value*, never a rejection test). *Plugin file:* still carries the generated marker (`:65`, `:582`) at the generated filename (`:110–111`). Each artifact's evidence authorises **only that artifact** | Non-resolving MCP entry → entry untouched **even if** the plugin is owned; markerless plugin → plugin untouched **even if** the entry is owned. The existing mechanics must be restricted accordingly: today's apply unconditionally overwrites entry and plugin (`:1042–1046`) and uninstall removes every old-named entry it finds (`:1054–1062`) — neither may be reused across an unqualified artifact |

Where evidence is ambiguous, the design does not claim provenance the old installation never recorded: the entry is left byte-identical, reported as needs-attention in install status (`get_install_status`, `:833`), and #791 describes it. Only unambiguous entries are rewritten without a manual step; that is the honest limit of “automatic”, and the normal-upgrade tests below use installer-created entries, which meet their evidence rows.

*Staged, recoverable execution.* Removal-then-apply with the current helper can destroy its own recovery point: `_backup_before_mutation` names archives at second resolution and opens them for writing (`:693–699`, `:734`), so a backup → remove → backup sequence inside one second can overwrite the first backup, and its failures are only logged (`:754–755`). The upgrade step therefore requires: (a) **preflight** — classify every provider and capture every value to be carried across before mutating anything; abort that provider's stage if capture fails; (b) **unique durable backups** — collision-free names (unique per attempt, never opened over an existing archive), file-and-directory flushed, verified readable, landed in the **new** backups folder (hence sequenced after section 4.6) and recorded like other backups as an absolute `Backup.file_path` (section 4.6.6); backup failure blocks that provider's mutation instead of proceeding; (c) **persisted per-provider stage** (for example `detected → backed-up → old-removed → new-applied → verified`) written durably before each destructive step, so an interruption after removal — when no old entry remains for a detector to find — still resumes forward on the next start, or rolls back from the recorded backup, without any manual repair command; (d) **both-name conflicts** (old and new entries both present, whether from an interrupted prior attempt or a hand-made new entry): merge nothing blindly — if the new entry meets the new-name evidence and carries the captured values, finish by removing only the qualifying old entry; otherwise stop that provider untouched beyond its backup and report needs-attention; (e) **failure surfaces**: CLI removal failures (Codex `:979`, Copilot `:1025`), routines that regenerate defaults instead of preserving captured customised values, unwritable files and missing CLIs each leave the provider at a recorded stage to retry on a later start, never half-rewritten silently. OpenCode regenerates its plugin under the new filename/marker/export and deletes the old file only while the old marker is present; Copilot's hooks filename follows the server name within the same stage. Ordinary recovery — retrying a recorded stage on a later normal start — must never require the operator to run a separate repair command. Keep the three outcomes distinct: a **recovery point** (durable backup + recorded stage) is not a completed migration; **completion** for an evidence-qualified provider is only a verified working new registration carrying the captured values; a **persistent** failure (missing CLI, unwritable state) is reported honestly as an incomplete named stage that ordinary restarts keep retrying, never as success. Only an *ambiguous* entry (above) resolves to a documented, operator-owned Mail-setup action in #791, because the product cannot honestly claim that entry as its own. Configuration written entirely by hand under the old name stops resolving at v4.0.0 and is listed there as a breaking change.

The MCP protocol test client name `claude-deck-test` (`backend/app/services/mcp_service.py:600`, `:865`) and the shim heartbeat thread name `claude-deck-agent-mail-heartbeat` (`backend/mcp_shim/agent_mail_server.py:303`) are emitted identifiers with no stored counterpart; they rename with the code.

#### 4.6.2 Ordering: the move must happen before first touch

Importing `app.database` freezes the engine's URL from settings (`backend/app/database.py:12`, `:23–28`) but opens nothing — SQLAlchemy connects lazily ([SQLAlchemy engine configuration](https://docs.sqlalchemy.org/en/20/core/engines.html#engine-configuration)). The first connection (`init_db`'s `create_all`, `:1161–1162`, from the lifespan at `backend/app/main.py:25`) is what would create a brand-new empty database at whatever path the frozen URL names. Two things must therefore be settled before that first connection: which *effective* locations are eligible (resolved with the **old** defaults as the comparison basis, before any default value changes — section 4.6.4), and the file move itself. The design invariant is:

> **Before any engine built from the new code's settings makes its first connection — and before any other code path can create files at the new locations — eligibility has been resolved against the old defaults and the first-start move for eligible resources has completed (or ruled itself out).**

Mechanisms are the implementation team's choice (for example a small pre-import bootstrap in the product's process entry point, before `app.main` / `app.database` import), but any mechanism must satisfy the invariant for the way the product is actually started — including the product-factory unit's `uvicorn app.main:app` command (`scripts/product-factory/claude-deck-product.service:13`) — and the test list (section 7, T-D3) proves no empty new file can appear first. Direct library imports of `app.database` by the operator's own scripts are outside the supported entry points; #791 should say the first run after upgrading must be the product itself.

#### 4.6.3 Conflict matrix (database)

Decided by this design where the Director left conflict behaviour to #789. The unit of decision is the **whole file set** (main file plus each of `-wal`, `-shm`, `-journal`), never the main file alone, and a validated move journal (section 4.6.5) always takes precedence over this existence matrix: a state the journal explains is resumed, not reclassified as a conflict. “Populated” means a non-empty file; a zero-byte main file is an uninitialised artefact — but zero-byte main **plus** a non-empty target sidecar is still populated target state and is never overwritten.

| Old file set | New file set | Journal | Behaviour |
|---|---|---|---|
| Absent | Absent | none | Fresh install: create only the new set. No old name is ever written |
| Populated | Absent (no main, no sidecars) | none | **Normal upgrade:** move the set per section 4.6.5, then start |
| Absent | Populated | none | Already upgraded (or restored by hand): no-op; never consult the old paths again |
| Populated | Only a zero-byte main file; no sidecar has content | none | The zero-byte file is recorded in the journal, then removed inside the same move before the set lands; never silently replaced by an unjournalled rename |
| Populated | Any sidecar has content (with or without a main file) | none | **Stop** as an unresolved conflict (target state of unknown provenance): abort before opening any database, preserve every source and target file byte-for-byte, report all paths |
| Populated | Populated | none | **Stop**: do not merge, pick a winner, or delete either set; abort before opening any database with an operator-visible message naming both locations. The only database outcome needing a human, and unreachable from the normal sequence |
| Anything | Anything | **valid journal present** | Resume the journalled plan (section 4.6.5) — including the cross-filesystem case where the target set is already durably in place and only journalled source removal remains, which then completes as a move, not as a both-populated conflict |
| Anything | Anything | journal present but **invalid or mismatched** to the files on disk | **Stop** with all data preserved; a journal that does not validate explains nothing and authorises nothing |

The home data folders use a file-level version of the same discipline, because their records are live (section 4.6.6), not inert history. If only the old folder exists it is renamed as a unit where possible. If both folders exist, files move one-by-one under the journal with **no overwriting**: a target name that is already taken is never replaced; instead the incoming file is allocated a fresh, collision-free target name *inside the journal* and the allocation is recorded so section 4.6.6 can point the owning record at the file that was actually moved. Only when an incoming file cannot be allocated and mapped losslessly does the folder move stop for that file — reported by name, old file left in place — and the upgrade does **not** declare that record migrated. The old folder is removed only when it ends empty.

#### 4.6.4 Eligibility, resolved per resource before anything changes

Each resource — database file set, backups folder, attachment folder — decides eligibility **independently**, by comparing its *effective resolved location* against that resource's old shipped default. One resource being custom never disables another resource's move: a custom database with default backups still migrates its backups and their references; default database with custom attachments still migrates the database. The combinations are tested as combinations (T-D6).

Resolution happens in the pre-connection bootstrap (section 4.6.2), reading the same environment/settings the old version read, with the old defaults still the basis — the new defaults must not have overwritten them yet. Concretely:

- an **unset** value resolves to the old default → eligible;
- a value **explicitly configured to exactly the old default** (same resolved absolute path after `~`/relative normalisation) is eligible — the data lives at the old-default location and must move like any other default install — **and** the conversion records the durable location binding defined below, because the operator's environment/`.env` value itself does not change when the files move;
- any other resolved value → custom for that resource → not moved, including a file that merely shares the default's **basename** in a different directory (comparison is by resolved path, never by name pattern);
- `:memory:` and non-SQLite database URLs are never eligible, and the `test_instance` mode (`backend/app/config.py:75–79`) disables every move outright;
- the attachment *agent root* (`bridge_attachment_agent_root`, `backend/app/config.py:34`) is a display-mapping root, not a storage location (section 4.6.6): it is never itself moved, and a custom agent root does not change storage eligibility;
- a custom `bridge_attachment_dir` resolving outside `~/.claude-registry/` is simply ineligible. One resolving *inside* the old home folder (for example `~/.claude-registry/my-attachments`) is the nested case: the home-folder rename would physically carry it along while its resolved setting would go stale. For that case the whole-folder rename is forbidden; the eligible default subfolders move individually, nested custom locations are left where they are (the old folder then necessarily remains, reported as such), and their stored references — already absolute and still correct — are untouched. Promising every custom location “untouched” without this case would be false, and silently carrying it along would be worse.

**Overlap/containment preflight (all resources, before any containing-directory move).** Eligibility alone is not enough when locations nest: before renaming *any* directory, resolve every configured resource location (database file, backups, attachments, agent root excluded as display-only) and compute containment both ways against every directory proposed for movement. A custom location strictly inside a candidate directory — attachments at `~/.claude-registry/backups/uploads`, a custom database file inside the old home folder — blocks that containing move as a unit. The preflight then chooses, per affected directory, either per-file movement that provably leaves the excluded subtree in place (with its contents and references untouched), or an explicit reported conflict that stops that directory's move — it never silently relocates an ineligible resource. Containment in the other direction (an eligible resource containing another resource's location) is ordered innermost-first under the same journal. Any overlap the preflight cannot classify is a stop, not a guess.

**Durable binding for migrated explicit defaults (chosen protocol).** Moving files does not edit the operator's environment or `.env` (settings still load both, `backend/app/config.py:9–13`), and the engine/attachment code use the configured values (`backend/app/database.py:23–28`; `backend/app/services/agent_bridge/attachments.py:237–238`) — so without a binding, `DATABASE_URL=…/claude_registry.db` would recreate the old file on the very first connection. The conversion therefore writes a product-owned **location-binding record**: a small durable file (written and file-+directory-synchronised like the move journals) at a deterministic location the pre-connection bootstrap can always find without opening any resource — inside the proposed new home data folder, reached by computing that proposed default, never by following the configured value. Per converted resource it records the captured old resolved path, the new resolved path, and the journal identity that performed the move. Resolution on every later start is then exactly:

1. Resolve the configured value as above. If no binding exists for that resource, section 4.6.4 eligibility decides as before.
2. If a binding exists and the resolved configured path **equals the captured old path**, the effective location is the bound new path. The old literal is consumed only as the key of this one recorded conversion — it is never opened, created or read as a location, which is what keeps this a conversion record rather than an ongoing alias or a manual-edit instruction. Nothing in the operator's launch files is read for writing or modified.
3. If the configured value is now anything else — the bound new path itself, or a different path the operator later chose on purpose — the configured value wins outright and the binding for that resource is retired (recorded, then removed): an intentional later change always outranks the conversion record, and is never overridden twice.
4. If the value becomes unset, the new shipped default already names the new location and the binding is redundant; it is retired the same way.
5. If a binding exists but its new target is missing, startup stops with the binding and journal evidence preserved; it never falls back to recreating or reopening the old location.

The binding record is written *before* the file-move journals close and is only retired under rules 3–4, so a second start with the operator's original environment/`.env` byte-identical still reaches the moved data (T-D6, T-G2). It is product-owned state in a product-owned folder; the no-manual-edit and ownership boundaries are intact.

#### 4.6.5 Crash safety, partial moves and idempotence

The move runs while the old version is stopped (section 5 makes quiescence a prerequisite, since an open WAL database must not be renamed under a live writer) — but a stopped old version does not prevent **two new-version starts racing each other**, so exclusivity is part of the protocol, not an assumption. These are design obligations for the implementation; the mechanism (lock primitive, journal format) is its choice within them.

1. **Exclusive ownership first.** Before inspecting or mutating anything, the bootstrap takes an exclusive, non-blocking migration lock anchored outside the paths being renamed (so the lock itself survives the rename). A start that cannot take it either waits for the holder to finish and then re-evaluates from scratch, or exits with a clear “upgrade in progress” message — it never proceeds concurrently, and it never treats the holder's half-moved state as a conflict. The lock is released only at a journalled terminal state.
2. **Durable intent before mutation.** Under the lock, write the move journal — a uniquely named record, itself outside the renamed paths (for example beside the new home folder's parent, never inside a folder that will move) containing: a journal identity/version, the eligible resources, exact source and target paths for **every file in each set** (including collision allocations from section 4.6.3), per-file expected state, and the current stage. The journal file **and its containing directory** are synchronised to storage before the first rename ([fsync](https://man7.org/linux/man-pages/man2/fsync.2.html) distinguishes the two; both are required at every destructive boundary below). A journal whose identity, paths or digests do not match the files on disk is invalid and stops the start (matrix, last row).
3. **Whole-set, no-replace movement.** Validate the entire source and target sets against the journal before moving. Each file lands by a no-replace operation: plain `rename(2)` *replaces* an existing target ([rename](https://man7.org/linux/man-pages/man2/rename.2.html)), so the implementation must use a no-clobber primitive (or an equivalent link-then-unlink discipline) and treat `EEXIST` as “stop and re-validate”, never as success. Sidecars move before the main file, whose arrival remains the set's commit point; the containing directory is synchronised after each file lands and again when the set completes. Renames preserve inode metadata (mode, ownership, times) by construction; the copy fallback (step 4) must preserve mode and ownership explicitly and record any metadata it could not preserve.
4. **Cross-filesystem copy with verified durability.** Where rename reports a cross-device error, copy each file to a journalled temporary name *in the target directory*, synchronise the file, and verify content identity by **cryptographic digest recorded in the journal before copying** — size alone never establishes identity. Only a verified copy is no-replace-renamed onto its target name and directory-synchronised; only after the **whole set** is durably in place and re-verified may sources be unlinked, each unlink followed by synchronising the source directory. A digest mismatch, short write or failed synchronisation discards the temporary copy, leaves every source byte untouched, and aborts startup. A crash after the target set is durable but before source unlinking finishes is a valid-journal resume (step 5), not a both-populated conflict.
5. **Journal-precedence recovery, in two digest phases.** The protocol deliberately separates an *immutable-file phase* from a *database-open phase*, because after first connection the database legitimately mutates and its file digests will change. While a file set is still in the immutable phase (no database has been opened against it), resuming validates presence **and** the journal-recorded digests. The database file-move journal reaches its terminal `landed` state — set complete, durable, sources dealt with — and is closed (removed + directory sync) **before** the first connection is allowed. From that instant no file-digest rule applies to the database again. Resources needing reference retargeting carry a *separate* reference journal (its own identity, mapping and stage) that survives the open; its replay never consults whole-file digests, only its own recorded mapping and the database's committed references-done stamp (step 6). That is why a crash immediately after a reference commit is a resume, never an “unexplained digest mismatch”: nothing is comparing post-open file bytes to pre-open digests.
6. **Durability barrier before retiring recovery information.** At the pin every SQLite connection runs WAL with `synchronous=NORMAL` (`backend/app/database.py:38–39`), under which a commit can survive a process crash yet be lost on power failure ([SQLite synchronous modes](https://www.sqlite.org/pragma.html#pragma_synchronous); [WAL behaviour](https://www.sqlite.org/wal.html#performance_considerations)). SQL commit alone is therefore **never** grounds for deleting a reference journal. The retargeting transaction and its references-done stamp must pass a verified durability barrier first — an appropriate SQLite mechanism the implementation chooses and the tests exercise (for example a `FULL`-synchronous transaction followed by a completed WAL checkpoint, or an equivalent that provably survives power loss) — and only then may the reference journal be removed and its directory synchronised. If the barrier cannot be verified, the journal stays, the stage stays open, and the next start replays the idempotent retargeting. Completion remains per-resource: files landed **and** references durably stamped **and** journal retired.
7. **Failure handling is phase-specific.** *Pre-open* failures (lock, journal validation, whole-set movement) abort before any database is opened, preserving every source. *Reference-phase* failures (transaction, stamp, durability barrier) stop before ordinary services rely on those references (section 5, step 2), leave the reference journal and the landed files exactly as they are — no rollback of landed files is attempted — and resume automatically on the next start. In either phase nothing is deleted except as a journalled step requires, and no state reached by crashing between journalled steps needs improvisation.

#### 4.6.6 Persisted path references migrate with their files

Moving files without their database references leaves retained-but-unusable data, because current readers use the stored strings directly:

|---|---|---|
| `Backup.file_path` (absolute) | Written `backend/app/services/backup_service.py:609–619` (model `backend/app/models/database.py:47`) and by the installer's pre-mutation backup `backend/app/services/agent_mail_install_service.py:744–753`; read directly for download, contents/manifest, validate and restore (`backup_service.py:651`, `:661`, `:694–699`, `:813`, `:944`; `backend/app/api/v1/backup.py:53`, `:168`, `:191`, `:296–302`) | Rewrite when it resolves **under the old backups root** to the journal's actual target path for that file (collision allocations included) |

Rules for the rewrite itself:

- **Matching is by ownership, not substring.** A value qualifies only if, after normalisation, it is the old root itself or a path beneath it *and* the journal maps that exact file. Values pointing elsewhere (custom locations, other drives, hand-edited paths, the nested-custom case of section 4.6.4) are untouched. A qualifying prefix with no journal entry (file missing at move time) is **ambiguous**: leave the value unchanged, surface it in the first-start report, and never guess a target.
- **Custom roots stay custom.** Attachments stored under a custom `bridge_attachment_dir` outside the old home are not retargeted; a custom `bridge_attachment_agent_root` (`attachments.py:243–246`) only changes how `agent_path` is *re-derived* — the stored agent root value itself is operator configuration, changed by nobody.
- **Ordering and transaction shape.** Files land first and their file-move journal closes *before* the database opens (section 4.6.5 step 5); the separate **reference journal** survives. On the opened database, one transaction retargets a resource's references and writes its references-done stamp; the reference journal is retired only after the section-4.6.5 step-6 durability barrier verifies that transaction power-loss-durable — commit alone (WAL `NORMAL`, `backend/app/database.py:38–39`) is not enough. Replay consults the stamp: stamp durably present → retire the journal without rewriting; stamp absent or not yet durable → re-run the idempotent retargeting (old-root values rewritten, already-new values skipped) and re-attempt the barrier. No “already migrated” inference is ever drawn from file presence alone.
- **Unrelated history is preserved.** Message bodies, charters, audit records and any other text that merely *mentions* an old path are history (section 4.3): never rewritten. Only the three structured references above — each with a named current consumer — are in scope.
- **Proof obligation.** Retention is only proved when pre-upgrade backups download and restore, and pre-upgrade attachments list, paste, delete and expire correctly, *through the current readers* — including the collision-allocation case where a record must follow its renamed file (section 7, T-D1/T-D7/T-D8). Checksums of moved files alone prove nothing about usability.

**Downgrade limits (the honest contract for #791).** There is no supported automatic downgrade, and “stop, rename back by hand” is **not** a sufficient rollback after first start, because v4.0.0 will also have rewritten provider configuration (section 4.2), browser storage (section 4.7) and the stored path references above, and may have created new backup rows and written new data under new names. #791 must therefore document rollback as a full pre-upgrade restoration (restore the pre-upgrade database, home folder and provider configuration from the operator's pre-upgrade backup, discarding post-upgrade state) with that data-loss boundary stated plainly — or omit a rollback promise entirely. v4.0.0 implements no rename-back behaviour.

### 4.8 Opaque constants: preserve, do not "rename"

Preserving such a constant is **not** old-name support: it accepts no old-name input, presents no old name to any user, and changing it would silently invalidate existing data. This class must stay narrow; anything a user, agent, script or another program can observe or supply belongs to sections 4.1–4.7.

## 5. The first start of v4.0.0, end to end

**Prerequisite (operational, not a code path):** the standard upgrade stops the old version first. No v3.1 process, dispatch scheduler or agent session may be mid-flight while data files are renamed. Sessions are long-lived children carrying group-A/B′ environment variables, old headers and a running old shim process (`backend/mcp_shim/agent_mail_server.py:13–14`, `:125`, `:247–248`); after the upgrade only new sessions — launched by the new backend with new variables, new headers and the new shim — are supported. Work belonging to those sessions is preserved in the moved database and git workspaces, but their credentials are **not** carried into authorization: closed/stale sessions stay rejected (section 4.5), relaunched shims register fresh sessions and receive fresh capabilities through the existing registration path, and no lifecycle, lease-expiry or HOLD check is bypassed or extended by hash continuity. #791 states “stop the old version, let running teams finish or be stopped, then start the new version”; that is part of a normal major upgrade, not an extra migration step.

The first start then performs, in this order:

1. **Exclusive, pre-connection data move.** Take the migration lock, consult any location-binding record, resolve eligibility and run the containment preflight per resource against the old defaults (section 4.6.4), then apply sections 4.6.3/4.6.5: resume a valid journal or start the journalled file moves, aborting before any database is opened on an unresolved conflict or unrecoverable failure. (Reference retargeting cannot happen yet — it needs the opened database — so resources with references stay journal-open at this point by design.)
2. **First database connection and reference retargeting.** Only now — database file-move journal closed, effective locations bound (section 4.6.4) — may the engine connect; run the existing `create_all` + compat-migration sequence (`backend/app/database.py:1156–1165`) from the lifespan (`backend/app/main.py:25`), then each open reference journal's section-4.6.6 transaction (retarget + stamp), pass the step-6 durability barrier, and only then retire that reference journal. Against a moved file `create_all` is the same no-op-plus-compat behaviour as any restart; only a fresh install creates tables. A retargeting or durability-barrier failure leaves the reference journal open for automatic resumption on the next start and is reported before ordinary services rely on those references; landed files are never rolled back for a reference-phase failure.
3. **Evidence-gated provider rewrite.** Run section 4.2 per provider from its persisted stage: preflight classification and value capture, unique durable backup into the new backups folder, staged remove/apply/verify with retry or rollback on later starts. Ambiguous entries stay untouched as needs-attention; no ordinary recovery needs a manual repair command. Pi takes no part here.
4. **Ordinary startup continues.** Attachment cleanup, scheduler start and relay cleanup follow their existing order (`backend/app/main.py:26–43`) — now against retargeted `storage_path` values under the new root, so cleanup unlinks the files the move actually placed. New sessions (including Pi launches with group-B′ environment and the regenerated extension/manifest) carry only new identifiers and register through the normal fresh-session path.
5. **First frontend load.** The served v4.0.0 frontend performs the one-time browser-storage copy-then-delete (section 4.7) and uses only new headers thereafter.
6. **Operator-visible record.** Startup reporting (and install status for step 3) states plainly: per resource what moved (old path → allocated new path) and which references were retargeted, any ambiguous reference or provider left needs-attention, any journal still open for automatic resumption, and — for group-C variables (section 4.1) — the value-free warning if old-prefixed names were present. No tokens, lease values or other credentials are logged.

Every later start re-enters the same stages cheaply: lock, journal check (resume or no-op), eligibility already settled by the absence of eligible old locations, provider stages already verified. Completion is defined by closed journals and verified stages — never by a “migration done” flag that could be set while work remains.

## 6. What deliberately breaks at v4.0.0 (input to #791)

This design implements the decided clean break. The release notes and migration guide (#791) must name at least:

1. `CLAUDE_DECK_*` variables set by hand (instance name/id/accent, external-actor token) are ignored until renamed (section 4.1, group C).
2. Agent configuration naming the old MCP server that the upgrade cannot evidence as product-installed — hand-written entries and ambiguous entries alike — stops resolving and is surfaced as needs-attention; only evidence-qualified installer entries are rewritten automatically (section 4.2).
3. Prompts, charters, skills and scripts that call `deck_*` tools must use the new public tool names; no aliases exist (section 4.3). External scripts matching `deck_unreachable` / `deck_http_error` error codes must match the new codes (section 4.4 rows 8/15).
4. Scripts calling the HTTP API with `X-Deck-Operator-Token`, `X-Deck-Session-Token` or `X-Claude-Deck-Terminal-Token` must send the new header names. Token *hashing* is unchanged, but authorization lifecycle is unchanged too: stopped sessions do not resume with old credentials — relaunched shims register fresh sessions (sections 4.5, 5).
5. Per-resource defaults move independently: operators who scripted against a **default filename** (`claude_registry.db`, `~/.claude-registry/...`) must update those scripts for each resource that moved; a resource they deliberately customised stays exactly there (section 4.6.4).
6. Release-download scripts must use the new artifact names (section 4.7). Existing GitHub label names keep working for existing scopes; only new scopes default to new labels (section 4.7).
7. There is **no rename-back rollback**: after first start, files, stored path references, provider configuration and browser state have all moved. The only documented recovery is full restoration of pre-upgrade state from the operator's pre-upgrade backup, discarding post-upgrade state, with that boundary stated plainly (section 4.6.6).

Do **not** assert whole-database byte identity after first open: retargeting, compat migrations and new metadata rows legitimately change bytes (T-D1 covers meaning).
- **T-D3 No empty-database race.** Start the new version against the fixture through every supported entry point and assert no new database file is created before the journalled move commits the set; the first health/API response already serves fixture data.
- **T-D4 Whole-set conflict matrix.** Every row of section 4.6.3, including: target sidecars with content but no (or only a zero-byte) main file stop with all files preserved; both-populated without a journal aborts before opening any database; a valid journal explaining a both-populated cross-filesystem state resumes to completion instead of conflicting; an invalid/mismatched journal stops with all data preserved.
- **T-D5 Crash, power loss, concurrency and failed writes.** Interrupt at each stage — journal write, each sidecar, main-file commit, copy, verify, each source unlink, directory synchronisation failure, folder allocation, reference transaction, **after SQL commit but before the durability barrier, after the barrier but before journal deletion, and after journal deletion** — and restart: the upgrade completes exactly once with no file lost, duplicated or replaced, and a further start is a clean no-op. The commit/barrier/deletion boundaries require a power-loss-grade fault model (for example a filesystem/power-cut harness that can drop non-synchronised WAL state): assert a commit that never passed the barrier is replayed from the surviving reference journal, never mistaken for a digest conflict; a process-kill-only run is recorded as insufficient evidence for this boundary, not as a pass. Two simultaneous new-version starts: exactly one owns the migration; the other waits or exits cleanly and never observes or worsens a half-move. Injected write/sync failures abort with every source byte intact.
- **T-D6 Per-resource eligibility combinations.** Cross the three resources (default vs custom database — including `:memory:` — × default vs custom attachments, backups always at their default computation in this fixture): each default resource migrates (with references) regardless of the others' custom choices; each custom resource is untouched **in location and unrelated data** — a custom database keeps its path while its `Backup.file_path` rows and new metadata rows still update inside it, so byte identity is never asserted. Explicit old defaults migrate like unset ones **via environment and via `.env` separately, with those operator files left byte-identical across two consecutive starts**: both starts use the moved data through the durable binding and no old-default file is ever recreated; then changing the value intentionally retires the binding and the new value wins. A same-basename file in another directory never moves; `test_instance` moves nothing. Containment preflight cases: custom attachments as a sibling inside the old home, attachments nested under `backups/`, and a custom database file inside the old home — no ineligible file or subtree changes location, bytes or references, and any unclassifiable overlap stops loudly.
- **T-D7 Folder collisions stay lossless and mapped.** Both home folders pre-exist with a colliding backup filename (different bytes) and a colliding live-attachment path: no target file is overwritten (digests before/after), each incoming file lands at its journal-allocated name, and each owning record (`Backup.file_path`; attachment `storage_path`/`agent_path`/`prompt_text`) points at the file that was actually moved — proved by downloading/restoring that backup and pasting/deleting that attachment. An allocation that cannot be mapped stops that file loudly without declaring it migrated.
- **T-D8 Ambiguous stored references.** Rows whose stored path has an old-root prefix but no file in the journal, rows under custom roots, and a custom `bridge_attachment_agent_root` configuration: ambiguous values are byte-identical after upgrade and reported; custom-root attachments still list/paste/delete; `agent_path` for migrated attachments is re-derived under the custom agent-root rule; unrelated message/charter text mentioning old paths is byte-identical (no blanket replacement).

### Installer, environment and Pi (sections 4.1–4.3)

- **T-I1 Evidence-qualified rewrite, per installed provider.** Standard upgrade leaves: no registration under the old server name; a working registration under the new name (MCP `tools/list` returns exactly the 36 public new names — Pi-mode private registration is T-P1); captured customised values (non-default URL) preserved under renamed keys; a unique, readable pre-mutation backup in the new backups folder, recorded with a working stored path.
- **T-I2 Ambiguity is never claimed as ownership — per artifact.** Hand-written entries that satisfy the *old* name/substring/key checks but fail the section-4.2 evidence rows are byte-identical after upgrade and reported needs-attention; an OpenCode entry with a customised URL but resolving command **is** rewritten with its URL preserved. Mixed OpenCode cases complete the matrix: owned marked plugin + unrelated MCP command (plugin replaced, entry byte-identical) and owned MCP entry + markerless plugin (entry rewritten, plugin byte-identical) — proving neither artifact's evidence leaks to the other and the overwrite/loops in today's apply/uninstall are not reused across an unqualified artifact.
- **T-I3 Staged recovery without a repair command.** Interrupt or force transient failure at backup, remove, add, file-write and status points — including removal-CLI failure, failure immediately after old-entry removal, a same-second second backup, and both old+new entries present: restarting the product normally **finishes at a verified working new registration carrying the captured values** (proved by `tools/list`, as T-I1). An intact backup or a cleanly rolled-back old entry counts only as a recorded pending stage, never as a pass for T-I3. Separately, a persistent missing-CLI/unwritable failure stays at its named incomplete stage across restarts — honestly reported, automatically retried, never declared migrated. Routines that would regenerate defaults are caught losing captured values.
- **T-I4 Generated files.** Old-marked OpenCode plugin is replaced under the new filename/marker/export and the old file removed; markerless plugin file survives untouched (needs-attention). Copilot hooks follow the new server-name filename within the same stage.
- **T-E1 New-prefix only.** Started with only old group-C variables set, the new code behaves as if they are absent (emitting the value-free warning if adopted) and never reads their values; with new variables set, identity/provider/URL take effect everywhere the old ones did, including session launches.
- **T-P1 Pi launch surface, separately.** A new Pi launch receives only new group-B′ keys from `pi_mail_environment`, the shipped extension activates on the new opt-in key, the manifest registers the 36 public new tools, the private close-generation tool is registered only in Pi mode under its new private name and completes a close, and `whoami` succeeds through the renamed client path. No installer rewrite is involved.

### Tools, headers, sessions, storage, labels (sections 4.3–4.5, 4.7)

- **T-T1 Public tool surface.** Non-Pi registration is exactly the 36 new public names of section 4.3; Pi mode is those 36 plus exactly the one renamed private tool. No `deck_`-prefixed tool or alias is callable in either mode; an old name fails as unknown.
- **T-H1 Headers with an eligible live session.** Against a session that is still lifecycle-eligible, the new operator/session/terminal headers work end-to-end through frontend, shim and backend, and the old header names are refused. This test uses a live, unclosed, pane-valid session — it must not be built by reviving a stopped one.
- **T-H2 Standard stop/relaunch obtains fresh registration.** Stop the fixture's sessions, standard-upgrade, relaunch: the new shim registers a **new** session (fresh session key/row) and works fully; the pre-upgrade token presented afterwards is rejected exactly as v3.1 lifecycle rules reject it (closed/stale), while that session's history remains readable in the moved database.
- **T-S1 Browser storage.** First load with only old keys present copies both values to the new keys and deletes the old ones (stored operator token keeps working without re-entry; selected provider is kept); a second load performs no copy; pre-existing new keys are never overwritten by stale old ones.
- **T-L1 Labels.** After the standard upgrade, existing scopes still dispatch against issues carrying their stored (old) label; a scope created after the upgrade defaults to the new label names.

### Opaque constants, guards and recovery contract (sections 4.8, 5, 6)

- **T-O1 Golden bytes, unchanged gates.** For a fixed hostname and lease token, v4.0.0 derives the *same* instance ID and lease hash as the v3.1 code, capability-token hashes verify identically, and `deck_compat_migrations` rows are honoured (no compat migration re-runs destructively). Separately assert the negatives: an expired lease stays expired, existing HOLD/approval checks still refuse what they refused in the fixture, and a still-valid lease passes *because it was still valid*, not because hashing granted it anything.
- **T-G1 No-old-name guard with a narrow migration exception.** On the implementation branch, the inventory's primary search over executable/configuration paths returns only: history and dated records; the frozen constants of section 4.8 (each with its rationale); negative fixtures; this campaign's planning documents; and a **named, minimal one-time-migration module set** whose old-name literals exist solely to identify old paths, keys, registrations and markers for conversion. Tests must prove the exception is conversion-only: those literals are unreachable as ongoing input (no old env key is read for a value, no old tool/header/server name is accepted) once first-start stages complete. Any other hit fails the check.
- **T-G2 Idempotence and the honest recovery contract.** A second v4.0.0 start — including with explicit old-default environment/`.env` values still in place (T-D6) — changes no file, reference or config byte and recreates no old-default location. The documented recovery from #791, followed literally — restoring the *complete* pre-upgrade set (database set, home folder, provider configuration, browser state) from a pre-upgrade backup, with post-upgrade state discarded as documented — starts the fixture under v3.1 with its pre-upgrade data intact; and a partial rename-back (files only) is shown to be insufficient, matching the published contract rather than a promise the product does not keep.
