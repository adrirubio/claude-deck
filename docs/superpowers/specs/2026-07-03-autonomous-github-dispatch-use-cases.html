Autonomous GitHub Dispatch — Use Cases & Required UX

Companion to 2026-07-02-autonomous-github-dispatch-design.md and 2026-07-03-autonomous-github-dispatch-workflows.md. Each use case below asks one question: what does a human have to configure, up front, so the brain + agent team can make the right call unattended — and where the spec, as written, leaves that decision uncodified (the agent is left to guess, stall, or silently do the wrong thing).

Revised: V1–V7 and UC11 are now fixed in the design spec — those use cases below are marked Fixed with the fix explained in place of the original gap callout. V8 and the undocumented failed-state producer remain open, called out as such rather than silently marked resolved.

References to V1–V8 and B1/B2/C1–C3/D point back to findings from the two companion pressure-test documents.

UC1Simple defect, single area, human-merge policy

Codified

Trigger: issue labeled claude-deck-ready + area:backend, scope's merge_policy=human.

Decisions the brain must make

  • Is this issue in scope at all?
  • Which slot owns it?
  • Is the fix verified before a human sees it?
  • Should the brain click merge? (No — always defer.)

UX that codifies each decision

  • dispatch_label presence — mechanical yes/no.
  • area_labels exact match — mechanical, no judgment.
  • CI check-run polling — an external, objective signal.
  • merge_policy="human" — explicit, unambiguous.
No gap. This is the case the design was built around — every decision has a direct, mechanical input.

UC2Simple defect, auto-merge policy

Fixed

Trigger: same as UC1, but scope's merge_policy=auto.

Decisions the brain must make

  • Everything in UC1, plus:
  • Is it actually safe to click merge on this specific PR right now?
  • What happens if the merge call itself fails?

UX that codifies each decision

  • merge_policy="auto" — codifies the human's blanket risk tolerance for the repo.
  • Daily auto-merge cap — codifies a volume ceiling.
  • Now codified: merge-call failures branch into transient (retry, shares the CI-failure budget) vs. durable (fall back to the human-review path, no escalation) — §7a.
Fixed (V2). "Auto-merge" now has a decision procedure for the failure path, not just the happy path: a transient mergeability failure retries; a durable policy block (branch protection, unmet required review) falls back to treating the item exactly as merge_policy="human" would — a normal outcome, not a pipeline error.

UC3Feature spanning two areas, mid-task reassignment

Fixed

Trigger: backend SME starts work, discovers the issue also needs frontend changes.

Decisions the brain must make

  • Should this be split into two dispatches, or handed off wholesale?
  • Is the new owner actually available and running?
  • Did the handoff's context actually transfer?
  • Is the original owner's slot safe to reuse immediately?

UX that codifies each decision

  • Split-vs-handoff remains the owner's judgment call, unobserved — unchanged, and reasonably so (not every judgment call needs codifying).
  • Now codified: a two-phase protocol — handoff_initiated (owner) then handoff_accepted (target, not assumed) — confirms the new owner actually picked it up (V4).
  • Now codified: the per-slot busy-check reserves both slots while handoff_state="pending", closing the window where the original slot read as free mid-handoff (V5).
  • Now codified: an unaccepted handoff times out to escalated (handoff_not_accepted) instead of sitting silently unresolved.
Fixed (B1, V4, V5). Reassignment is now a two-message verified state transition, not a single bookkeeping write. The brain can tell "handoff in flight" from "handoff done," and the vacated slot is only freed once acceptance is confirmed — not assumed the instant the handoff was requested.

UC4Design/brainstorming issue → spec doc merged via PR

Partially fixed

Trigger: issue labeled claude-deck-ready + claude-deck-design.

Decisions the brain must make

  • Which pipeline applies (code vs. design)?
  • Who satisfies the human-approval gate the owner's own brainstorming skill requires?
  • When is the design "verified" (since CI proves nothing)?
  • When has the approval loop gone on too long?

UX that codifies each decision

  • design_label — mechanical, unambiguous.
  • Prompt instruction naming the leader as delegated approver — still codified as text, not an enforced backend gate (§11.7, unchanged this round).
  • awaiting_human_review state — codifies "a real human, not CI, decides."
  • Now codified (fixes V3): max_approval_rounds caps the back-and-forth; reaching it escalates instead of looping forever.
Partially fixed. V3 (no bound on the approval loop) is fixed. The deeper C1 weakness flagged in §11.7 is not: nothing stops a misbehaving owner from skipping the wait entirely and proceeding without leader approval — the round cap bounds a legitimate back-and-forth, it doesn't enforce that one happens. This is called out honestly in the spec as the single weakest link in how C1 is resolved, not glossed over.

UC5CI check fails after PR opened

Codified

Trigger: owner's PR has a red check-run.

Decisions the brain must make

  • Retry, or give up?
  • How many retries before it's not worth the owner's time (or cost)?

UX that codifies each decision

  • retry_count + per-scope retry budget — explicit, numeric, human-settable.
  • Escalation on exhaustion — explicit downstream state.
No gap in the decision itself — though see UC8: the state it escalates to has its own problem.

UC6Two same-area issues land in one poll cycle

Fixed

Trigger: issues #50 and #51 both match area:backend in the same poll.

Decisions the brain must make

  • Can both be worked at once, or must one wait?
  • How should a human reading the dashboard distinguish "waiting because busy" from "not yet processed"?

UX that codifies each decision

  • Hard per-slot concurrency cap of 1 — correctly codifies "one slot, one active task," no judgment needed.
  • Now codified: pending_reason ("queued_slot_busy" vs. null) distinguishes queued-behind-a-busy-slot from freshly-discovered in the activity feed (V6).
Fixed (V6). The brain's queueing behavior was always correct — the gap was purely that a human operator couldn't tell "stuck" from "queued" apart. The new pending_reason column closes that: the activity feed now reads "pending · queued behind Backend SME" instead of a bare, ambiguous "pending."

UC7Leader never comes online

Fixed

Trigger: owner sends a triage/approval message; leader's slot is offline or unresponsive.

Decisions the brain must make

  • How long to wait before treating this as stuck?
  • Should the wait differ for a code ack (low stakes) vs. a design approval (a real gate)?

UX that codifies each decision

  • Idle-timeout threshold, with a design-issue multiplier — now correctly scoped to only the genuinely ambiguous case.
  • Now codified: monitoring checks Agent Mail wake_state first — an offline leader escalates in one poll cycle; only a reachable-but-unresponsive leader falls through to the idle-timeout multiplier (V7).
Fixed (V7). The generous multiplier now applies only where it was actually meant to — a leader that's reachable but might be reviewing carefully. An actually offline leader no longer waits out that same generosity; it's detected and escalated the very next poll, since wake_state="offline" is a fact the brain can observe directly.

UC8Item escalates (any reason)

Fixed

Trigger: any escalation path — blocked plan, idle timeout, retry budget exhausted, zero check-runs, approval rounds exhausted, handoff not accepted, label removed.

Decisions the brain must make

  • What should happen after a human looks at an escalated item?
  • How does the item re-enter the pipeline once the human fixes whatever was wrong?

UX that codifies each decision

  • Notification on escalation — codified (Agent Mail broadcast + activity feed row + escalation_reason).
  • Now codified: a watcher rule resets escalated → pending on a fresh github_updated_at, mirroring the existing failed rule (§4 step 3a).
  • Now codified: a narrow "Retry" UI action wraps that same recovery rule, so a human doesn't have to go touch the GitHub issue by hand (§10).
Fixed (V1) — was the highest-leverage gap found, now the highest-leverage fix. Every escalation trigger across every other use case now feeds into a state that knows how to recover, instead of a dead end. This is also why the number of things that can escalate could safely grow in this revision (approval-round exhaustion, handoff timeout, label removal) without each one needing its own bespoke recovery path — they all reuse this one.

UC9Auto-merge API call itself fails

Fixed

Trigger: all checks green, brain calls PUT .../merge, GitHub returns a non-200 (branch protection, stale head, required review unmet).

Decisions the brain must make

  • Retry the merge call? Wait and re-check mergeability? Fall back to notifying a human?

UX that codifies each decision

  • Now codified: transient failures (405/409/unstable mergeable_state) retry next poll, sharing §7a's existing CI-failure retry budget rather than a new counter.
  • Now codified: durable failures (403 required review, branch protection) fall back to the human-review notification path — no escalation, since this is the repo's own rules correctly requiring a human.
Fixed (V2) — same fix as UC2. §7a now has exactly the small decision tree this use case was missing, and reuses existing infrastructure (the retry budget, the human-review notification) rather than inventing new machinery for it.

UC10Issue matches no area label, no slot has an expertise blurb

Partially codified

Trigger: an issue with no recognized area label, on a team where no slot has filled in expertise.

Decisions the brain must make

  • Who owns this if nothing distinguishes any slot?

UX that codifies each decision

  • Explicit fallback: route to the leader — codified, no ambiguity in the decision itself.
No decision gap — the fallback is well-defined. Worth flagging only that a team that never fills in expertise silently gets zero benefit from the classification step and every un-labeled issue piles onto the leader's slot, which is a capacity problem more than a decision problem (and one an operator would want surfaced, not just a routing default).

UC11Human removes dispatch_label after dispatch already happened

Fixed

Trigger: a human has second thoughts after Deck already dispatched and the owner is mid-implementation.

Decisions the brain must make

  • Does removing the label mean "stop the running agent," or does it only affect future polls?

UX that codifies each decision

  • Now codified: the watcher makes one extra call per poll re-checking label presence on already-active items by number (independent of the label-scoped query), and escalates with a notify-the-owner Agent Mail message if the label's gone (§4 step 3b).
Fixed, with an honest limit. Removing the label now reliably notifies the owner and escalates the item — a human's natural "stop this" gesture finally does something. It's deliberately "notify, don't kill": Claude Deck still can't safely force-terminate a mid-task tmux session (no clean way to avoid a half-written commit or dangling branch), so the owner's own judgment decides how to wind down. Flagged as an accepted tradeoff in the design spec, not oversold as a hard guarantee.

UC12Team spans two repos; issues land on both simultaneously

Codified

Trigger: a team with two TeamGithubScope entries gets a labeled issue on each repo at the same time.

Decisions the brain must make

  • Which repo does the owner slot's session actually work in?
  • Are the two repos' guardrails/merge policies independent?

UX that codifies each decision

  • repo_path_override at launch time — directly codifies working-directory selection per dispatch.
  • Guardrails and merge_policy scoped per TeamGithubScope row, not per team — correctly independent per repo.
No gap. This is the one multi-repo case the design explicitly built for and reasons through carefully (§3.3). Note it composes with UC6's per-slot cap: if both repos route to the same slot (e.g. one SME covers backend across both repos), the per-slot concurrency cap still applies correctly across repos, per §5b's explicit "regardless of which repo" wording.
