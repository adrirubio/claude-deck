Autonomous GitHub Dispatch — Deck UI Mockups

Companion to 2026-07-02-autonomous-github-dispatch-design.md, 2026-07-03-autonomous-github-dispatch-workflows.md, and 2026-07-03-autonomous-github-dispatch-use-cases.html. There are two ways to configure a team for autonomous GitHub work: the Deck UI (mockups below) and the API/agentic interface (REST + the deck_report_dispatch_status MCP tool an owner slot calls). This document mocks up the UI side only — every field shown here maps 1:1 to a field an API caller could set directly; the UI is a convenience layer over the same schema, not a separate capability.

Screens are annotated with which use case(s) from the use-case doc they exist to satisfy, and rendered against Claude Deck's actual color palette (dark theme, matrix-green primary) so they read as the real app rather than a generic mockup.

0. Two configuration paths, one schema

Before the mockups: nothing below is UI-only capability. Every field a human sets in these screens is a column on TeamGithubScope or AgentTeamSlot that an external actor (OpenClaw, a script, the MCP shim) can set via the same REST endpoints the UI calls. The UI's job is discoverability and validation, not gatekeeping a capability the API doesn't have.

The one row worth calling out: status reporting has no UI equivalent, on purpose. A human never manually sets "this item's PR is open" — only the dispatched agent knows that, and the design spec (§5d) makes the agent report it explicitly rather than have the brain infer it from prose. The UI only ever displays the result of those reports (Screens 5–7); it never originates them.

Why area labels and expertise are grouped in their own highlighted card, not just two more plain fields: UC10's finding was that a team that never fills these in silently gets zero routing benefit and every issue piles onto the leader. Visually separating "GitHub dispatch routing" from the slot's general identity fields is meant to make the omission noticeable — an empty highlighted card reads as "you skipped something," where two blank fields blending into a long form don't.

What "Retry" actually does (per the design spec §10): it's a thin wrapper around the same recovery rule the watcher already applies on its own — reset to pending, clear escalation_reason/retry_count/approval_round_count, re-route from scratch. There is deliberately no "edit and resubmit" or "force dispatch" button here — fixing the actual problem (the failing test, in this example) still happens in the code/issue, not in this dialog.
